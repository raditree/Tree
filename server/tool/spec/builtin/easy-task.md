## 判型确认（开工前必查）

**5 项判据必须全部满足才走 easy**（任一项不满足 → 上调 complex-task；命中架构级/高危判据 → 直接 hard-task）：

| # | 判据 | 判定说明 |
|---|------|----------|
| 1 | 单文件或 ≤3 个文件的局部改动 | 改动范围可穷举，不需要跨模块追影响 |
| 2 | 明确的问答、查资料类 | 或用户已给出精确改动点 |
| 3 | 预计 tool call ≤ 5 | 含读、改、验在内的总调用次数 |
| 4 | 无新增依赖、无接口变更 | 不动 pubspec/requirements、不改对外接口 |
| 5 | 改动影响面可预判 | 能在动手前列出受影响的行为 |

**典型正例（适合 easy）**：
- 改 UI 上一处文案/样式（单文件）。
- 修一个定位明确、修法明确的 bug（改一个函数）。
- 回答一个基于现有代码/记忆即可解答的问题。

**典型反例（不适合 easy）**：
- "把这个功能加上"——涉及多文件多处改动 → complex-task。
- "升级一下依赖并适配"——新增/变更依赖 → complex-task。

## 工作流（workflow）

1. **判型与澄清**：按上方清单判型；若用户意图模糊（改哪个文件、期望行为不明），
   用 `ask_user_question` **一次性**问清全部疑问，禁止靠猜。
2. **读上下文**：不确定目标文件时先用 `grep` 定位，再 `read` 精读相关文件（≤3 个）；
   大文件用 start_line/line_count 只读需要的段落，避免整读占用上下文。
   确认改动点与现状，**先读后写，禁止盲改**。
3. **直接执行**：
   - 已有文件局部修改 → `edit`（old_text 必须在文件中唯一匹配，不唯一先 `read` 确认再缩小范围）。
   - 新建文件或整文件重写 → `write`（写入前先 `read` 确认是否已有同名文件）。
   - 环境操作（跑命令/查环境/git 提交）→ `terminal`。
4. **验证**：用 `terminal` 执行验证命令（构建/测试/运行），确认改动生效且未破坏现有功能；
   预计耗时长的命令传 `hook=true` 后台执行，结束后读输出文件继续。
   - **验证失败处理路径**：读命令输出定位原因 → 修复 → 重验；**最多 2 轮**。
     仍失败 → 停止硬撑，升级 complex-task，并向用户如实汇报已尝试的修法与结果。
5. **汇报**：按"汇报模板"结构化输出；仅在确需用户决策时用 `ask_user_question`，通常直接汇报。

## 该类任务规范

- **单人单会话直接完成**：无需建 todo（`set_todo_list` 不用）、无需召集团队（`team` 不用）。
- **先读后写**：任何修改前先用 `read` 看清楚目标文件当前内容，禁止盲改。
- **最小改动范围**：只改任务要求的范围，禁止顺手优化、无关重构、风格统一等"顺手改"。
- **改后必验证**：用 `terminal` 跑构建/测试/运行，不能只写不验；验证失败按工作流第 4 步路径处理。
- **范围蔓延即重判型**：执行中发现要改的东西超出原判型范围，先停下重新判型，不得"边扩边做"。

## 汇报模板

按以下结构汇报（各项都给出；无内容的项目写"无"）：

```
【改动点】
- <文件路径>：一句话摘要
【修改原因】
<为什么这么改>
【验证结果】
- <验证命令>：<结论（通过/失败+原因）>
【影响面与潜在风险】
<受影响的行为；若无写"无">
【后续优化建议（仅建议，不实施）】
<可选；无写"无">
```

## 边界与异常处理

- **升级触发条件（任一命中即切换 complex-task，不得硬撑）**：
  - tool call 已超过 8 次仍未收敛；
  - 发现跨文件/跨模块影响；
  - 需要多方案比较才能定改法；
  - 需要新增依赖或变更接口。
- **目标文件不存在**：先 `grep`/`terminal ls` 确认路径，仍找不到 → `ask_user_question` 与用户确认目标。
- **edit 匹配不唯一**：回到 `read` 取更精确的上下文作为 old_text，禁止碰运气式多次试错。
- **用户中途追加需求**：判断是否超出本次 easy 范围；超出 → 重新判型（新增部分单独判型），不静默扩大改动面。
- **验证 2 轮仍失败**：升级 complex-task，汇报已尝试内容，禁止无限重试。

## 注意事项

- **easy 是初判，不是承诺**：若发现"以为简单但越做越复杂"，停下来重新判型，走对应 Spec。
- 回答类任务不要过度使用工具：资料在记忆/上下文里就直接回答，别为"看起来在干活"而调工具。
- 一次汇报讲清楚，避免拆成多条碎片消息；用户追问时按同结构补充。
