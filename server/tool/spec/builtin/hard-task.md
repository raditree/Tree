## 判型确认（开工前必查）

**任一命中即走 hard**：

| # | 判据 | 判定说明 |
|---|------|----------|
| 1 | 架构级、框架级变更 | 动分层结构/引入或更换框架/改核心抽象 |
| 2 | 新领域无经验 | 团队对该技术域无既有实践，方案需要探索 |
| 3 | 高不确定、需多方案比较 | 候选方案 ≥2 且优劣不明显，需评审定夺 |
| 4 | 高危操作 | 安全/性能/数据迁移/兼容性/不可逆变更 |
| 5 | 用户明示 | "重新设计 / 大重构 / 企业级 / 谨慎处理" |

**与 complex 的边界**：多文件改动但无架构影响、方案唯一明确 → complex 即可，不升 hard；
判型存疑时宁可上调（hard 可降级，complex 硬撑风险更高）。

## 工作流（workflow）

1. **检索 Spec**：`spec search`。
   - 明确命中适用 Spec → `spec read` + `spec select` 挂 hook，并**回归 complex-task** 流程执行。
   - 仅模糊命中 / 无命中 → 走下方企业级流水线。
2. **界定边界**：明确范围、**明确不做项**、约束条件、验收标准，
   写入 `.self/` 文档（可追溯）；同时用 `set_todo_list` 建立全任务计划（含各阶段评审点）。
3. **团队会议**：遵循 **team-meeting** Spec（会议期间只讨论、只产出方案，禁止落地）。
   - `team update_member` 激活架构/前端/后端/测试/安全等角色成员并设置分工；
   - `message send_message`（或 `message broadcast`）发起会议，各成员按角色给出方案（按 team-meeting 的发言模板）；
   - 汇总方案、按选型矩阵比较，用**决策记录模板**记录选型理由（写入工作空间方案文档）。
4. **标准团队开发流水线**（每阶段有产出物与评审，**不跳过任何阶段**）：
   需求分析 → 方案设计 → 方案评审 → 实现 → 测试 → 交付；
   每阶段的产出物、评审要点与准出条件见下方"流水线阶段标准"。
5. **高危确认**：涉及破坏性/安全/数据迁移等操作，`ask_user_question` 向用户确认后再执行，
   确认信息含四要素（见"风险评估框架"末尾的确认单）。
6. **补充 Spec**：**强制** `spec create` 沉淀本次经验（缺失则任务未闭环）。

## 该类任务规范

- **必须过会议讨论阶段**：hard 任务禁止直接动手实现，先开会定方案。
- **流水线每阶段有产出物与评审**：方案文档写入工作空间可追溯，阶段产物由团队评审，不跳过任何阶段。
- **高危必确认**：任何不可逆/高风险操作先 `ask_user_question`，禁止未确认执行破坏性命令。
- **末尾必补 Spec**：`spec create` 是本任务闭环的最后强制步骤，无论成功与否。
- **方案比较记录理由**：为什么选 A 不选 B，按决策记录模板写进方案文档。
- **全任务 todo 计划**：用 `set_todo_list` 建立，各阶段评审点作为独立 todo 项跟踪。

## 流水线阶段标准

| 阶段 | 产出物 | 评审要点 | 准出条件 |
|------|--------|----------|----------|
| 需求分析 | 需求说明（用户目标/功能点/不做项/验收标准） | 完整性/一致性/可验证性 | 验收标准可测、无歧义 |
| 方案设计 | 设计方案（模块划分/接口约定/数据流/风险） | 可行性/风险/成本/兼容性/可回滚 | 至少 2 个候选比较后定稿 |
| 方案评审 | 评审结论（团队评审记录） | 是否达成共识、风险是否可接受 | 评审通过才准实现 |
| 实现 | 代码 + 自测记录 | 按设计实现/编码规范/自测通过 | 偏离设计处已在决策记录追加说明 |
| 测试（整个流水线**最重要的一环**） | 测试报告 | 全量 + 关键路径 + 回归 | 全部通过（或遗留项经用户确认） |
| 交付 | 交付汇报（含验证结果与遗留项） | 汇报完整性 | 用户已知悉结果与风险 |

**评审不通过路径**：迭代设计 → 复审（最多 2 轮）→ 仍无共识 → `ask_user_question` 升级用户决策。

## 决策记录模板（ADR 风格）

写入工作空间方案文档（`.self/`），供追溯：

```
【背景与问题】
<为什么需要这个决策：现状、约束、要解决的问题>
【候选方案】
- 方案 A：<概述> / 优势：<…> / 劣势：<…> / 成本：<…>
- 方案 B：<概述> / 优势：<…> / 劣势：<…> / 成本：<…>
（可选方案 C…）
【选型结论】
<选定方案 X>
【选型理由】
<为什么选 X 不选 Y：结合评审要点与成员意见>
【风险与缓解】
- <风险>：<缓解措施>
【回滚方案】
<若实施后发现问题，如何回退/降级>
```

## 风险评估框架

- **概率 × 影响矩阵**：对每个已识别风险标注概率（高/中/低）与影响（高/中/低）；
  概率高×影响高 → 必须先定缓解措施再实施；写入决策记录的"风险与缓解"。
- **高危操作清单（命中即触发工作流第 5 步用户确认）**：
  - 数据迁移 / 批量删除 / 覆盖既有数据；
  - 安全相关（鉴权/加密/权限变更）；
  - 兼容性破坏（对外接口/存储格式/协议变更）；
  - 不可逆变更（删除源码/历史/配置无法恢复）。
- **高危确认单四要素**（`ask_user_question` 时必须给全）：
  1. 操作内容：具体要执行什么；
  2. 影响范围：波及哪些数据/模块/用户；
  3. 回滚方案：出问题如何恢复；
  4. 是否继续：请用户明确决策。

## 边界与异常处理

- **问题过大应拆分**：一个 hard-task 装不下时，按模块或阶段拆成多个 hard-task 分别处理，
  共享同一份决策记录与边界文档。
- **可降级**：会议中若发现不满足 hard 判据（实际只是多文件改动、无架构影响）→ 降级 complex-task 走其流程。
- **方案评审不通过**：按"流水线阶段标准"末尾路径处理（迭代 ≤2 轮 → 升级用户）。
- **实施中发现方案不可行**：停下 → 回退到方案设计阶段 → 在决策记录追加"实施反馈"与原因 → 重新评审，
  禁止边做边大幅偏离已评审方案。
- **高危操作被用户拒绝**：记录决策（用户选择），调整方案或终止任务，同样走 Spec 沉淀闭环。

## 注意事项

- **Spec 补充是最后强制步骤**：无论任务成功与否，务必沉淀经验到新 Spec，供后续复用。
- 高风险操作前必须确认，禁止在未确认情况下执行破坏性命令。
- 会议阶段严格遵循 team-meeting（只讨论不落地）；会后回到本流水线。
- 交付汇报中如实呈现遗留项与风险，不粉饰。
