## 工作流（workflow）

1. **检索 Spec**：`spec search`。
   - 明确命中适用 Spec → `spec select` 挂 hook 并**回归 complex-task** 流程执行。
   - 仅模糊命中 / 无命中 → 走下方企业级流水线。
2. **界定边界**：明确范围、不做项、约束条件、验收标准，写入 todo 首项或 `.self/` 文档。
3. **团队会议**：
   - `team update_member` 激活架构/前端/后端/测试/安全等角色成员并设置分工。
   - `team send_message` 发起会议，各成员按角色给出方案。
   - 汇总方案、比较选型，记录选择理由（写入工作空间方案文档，可追溯）。
4. **标准团队开发流水线**（每阶段有产出物与评审，不跳过）：
   - 需求分析 → 产出需求说明
   - 方案设计 → 产出设计方案
   - 方案评审 → 团队评审通过
   - 实现 → 按设计实现（协调成员并行）
   - 测试 → 全量验证
   - 交付 → 汇报用户
5. **高危确认**：涉及破坏性/安全/数据迁移等操作，`AskUserQuestion` 向用户确认后再执行。
6. **补充 Spec**：**强制** `spec create` 补充相应 Spec（缺失则任务未闭环）。

## 该类任务规范

- **必须过会议讨论阶段**：hard 任务禁止直接动手实现，先开会定方案。
- **流水线每阶段有产出物与评审**：方案文档写入工作空间可追溯，阶段产物由团队评审，不跳过任何阶段。
- **高危必确认**：任何不可逆/高风险操作先 `AskUserQuestion`。
- **末尾必补 Spec**：`spec create` 是本任务闭环的最后强制步骤。
- 方案比较记录理由：为什么选 A 不选 B，写进方案文档。
- 使用 `SetTodoList` 建立全任务计划（含各阶段评审点）。

## 注意事项

- **问题过大应拆分**：一个 hard-task 装不下时拆成多个 hard-task 分别处理。
- **可降级**：会议中若发现不满足 hard 判据（实际只是多文件改动），可降级为 complex-task。
- **Spec 补充是最后强制步骤**：无论成功与否，务必沉淀经验到新 Spec，供后续复用。
- 高风险操作前必须确认，禁止在未确认情况下执行破坏性命令。
