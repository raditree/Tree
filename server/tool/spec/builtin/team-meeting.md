## 适用场景与判型

**何时开会**：
- hard-task 流水线的"团队会议"阶段（强制）；
- 用户或 leader 明确要求"开会 / 讨论一下 / 先出方案"；
- 架构级/框架级变更需要多方案选型；
- 高不确定事项需要团队评审把关。

**何时不开会**：信息充分、方案唯一明确、可直接执行的任务（开会属浪费——直接走对应任务 Spec 执行）。

## 工作流（workflow）

1. **会议召集（leader）**：明确会议主题与目标、参会成员、需要的背景材料，
   用 `team send_message` 邀请相关成员参会，消息按"会议召集消息模板"撰写，
   **明确标注"本次为会议讨论，请只给方案/意见，禁止改代码、跑命令、派活"**。
2. **成员发言（成员）**：收到会议消息后，只围绕主题按"成员发言模板"给出：
   方案思路、理由与利弊、风险点、所需前置信息。
   **严禁**调用 write/edit/terminal/assign_task 等落地工具。
3. **方案汇总（leader）**：收集各成员方案，按"方案比较矩阵模板"比较选型，
   记录选择理由（写入工作空间方案文档，配合 hard-task 的决策记录模板）。
4. **定案与分工（leader）**：方案确定后，用 `team update_member` 明确分工，
   再发**明确的执行指令**（assign_task / send_message 注明"开始执行任务：xxx"）。
5. **进入执行**：收到明确执行指令后，成员方可按分工开始落地（写入/修改/验证）。
6. **会议纪要**：将结论、选型理由、分工与待办按"会议纪要模板"沉淀到
   `.self/`方案文档，供追溯。

## 该类任务规范

- **会议 ≠ 开工**：收到"会议 / 讨论 / 出方案"性质的消息，一律先只讨论；
  没有收到明确的"开始执行 / assign_task"指令前，**禁止**任何文件写入、命令执行、任务派发。
- **发言结构化**：按发言模板四要素（方案思路/理由与利弊/风险/前置问题），简明不冗长。
- **决策闭环**：leader 必须明确给出最终选型与执行指令，不能把会议悬空；成员收到指令后再动手。
- **产出可追溯**：方案与决策理由写入工作空间文档（`.self/`）。
- **发言轮次收敛**：每个议题成员发言 ≤ 2 轮；仍无共识 → 走"边界与异常处理"的收敛机制。
- **可结合 hard-task**：hard 流程中的"团队会议"阶段遵循本 Spec；会议结束后回到 hard-task
  流水线（需求→方案→评审→实现→测试→交付）。
- 会议期间如需了解现状，可用 `read` 读取相关文件辅助判断，但**不得修改**。

## 会议召集消息模板

leader 发 `team send_message` 时按此结构：

```
【会议主题】<一句话主题>
【会议目标】<要产出什么：如"确定 X 的技术方案">
【参会成员】<成员列表（按角色）>
【背景材料】<相关文件/现状/约束；成员可先 read 了解>
【会议纪律】本次为会议讨论，请只给方案/意见，禁止改代码、跑命令、派活。
【输出要求】请按"方案思路/理由与利弊/风险点/前置问题"四段发言。
```

## 成员发言模板

成员收到会议消息后按此结构回复：

```
【方案思路】<概述方案与关键做法>
【理由与利弊】<为什么可行；优势与劣势各列要点>
【风险点】<实施可能出问题的地方>
【前置问题】<需要 leader/用户先明确的信息；无写"无">
```

## 方案比较矩阵模板

leader 汇总方案时按维度对照（维度可按议题增删）：

| 维度 | 方案 A | 方案 B | （方案 C…） |
|------|--------|--------|-------------|
| 可行性 | <高/中/低 + 说明> | … | … |
| 实现成本 | <工作量/复杂度> | … | … |
| 风险 | <主要风险> | … | … |
| 可维护性 | <长期维护负担> | … | … |
| 回滚难度 | <出问题能否退回> | … | … |

比较结论与选型理由写入方案文档（与 hard-task 的决策记录模板配合使用）。

## 会议纪要模板

```
【议题与目标】<本次会议讨论什么、要达成什么>
【参会成员】<成员列表>
【讨论要点】<各方方案与分歧摘要>
【结论与选型理由】<最终选定的方案及理由>
【分工与待办】
- <待办事项>：<负责人> / <验收标准>
【风险与后续】<遗留风险与跟进计划>
```

## 边界与异常处理

- **召集消息未明确"只讨论"**：成员应**默认先讨论、不落地**，并可在回复中确认：
  "已收到会议议题，以下为方案建议，待确认后再执行。"
- **议题发散**：leader 主动收敛回主题（"回到本次议题 X，先聚焦 A 点"），不追发散点。
- **无共识收敛机制**：发言 ≤ 2 轮仍无共识 →
  leader 给出**默认方案**（含理由与风险）直接定案，或 `ask_user_question` 升级用户决策；
  **避免无限开会**。
- **成员缺席/未响应**：leader 按已到成员意见推进，纪要中记录缺席者与未采纳原因；
  关键角色缺席且方案涉及其领域 → 升级用户或延期再议。
- **把"收集方案"误当"分配任务"**：assign_task 只在定案之后使用，会议阶段禁止。
- **高危议题**：方案必须包含风险评估（参考 hard-task 的风险评估框架），落地前需用户确认。

## 注意事项

- 会议的价值在于**比较与决策**，不在于发言长度：每个发言控制在一屏内。
- 决策记录（矩阵 + 理由）是会议的核心产出，先于任何代码存在。
- 会议结束 ≠ 任务结束：定案后进入执行与验证（对应任务 Spec 流程），纪要中的待办需逐项闭环。
