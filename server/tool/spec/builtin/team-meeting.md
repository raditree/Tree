## 工作流（workflow）

1. **会议召集（leader）**：明确会议主题与目标，用 `team send_message` 邀请相关成员参会，
   消息中**明确标注**"本次为会议讨论，请只给方案/意见，禁止改代码、跑命令、派活"。
2. **成员发言（成员）**：收到会议消息后，只围绕主题给出：方案思路、利弊分析、风险点、
   所需前置信息。**严禁**调用 write/edit/terminal/assign_task 等落地工具。
3. **方案汇总（leader）**：收集各成员方案，比较选型，记录选择理由（写入工作空间方案文档）。
4. **定案与分工（leader）**：方案确定后，用 `team update_member` 明确分工，再发**明确的执行指令**
   （assign_task / send_message 注明"开始执行任务：xxx"）。
5. **进入执行**：收到明确执行指令后，成员方可按分工开始落地（写入/修改/验证）。
6. **会议纪要**：将结论、选型理由、分工与待办沉淀到 `.self/` 或 docs/ 方案文档，供追溯。

## 该类任务规范

- **会议 ≠ 开工**：收到"会议 / 讨论 / 出方案"性质的消息，一律先只讨论；没有收到明确的
  "开始执行 / assign_task" 指令前，**禁止**任何文件写入、命令执行、任务派发。
- **发言结构化**：方案 + 理由 + 风险 + 前置问题，简明不冗长。
- **决策闭环**：leader 必须明确给出最终选型与执行指令，不能把会议悬空；成员收到指令后再动手。
- **产出可追溯**：方案与决策理由写入工作空间文档（.self/ 或 docs/）。
- **可结合 hard-task**：hard 流程中的"团队会议"阶段遵循本 Spec；会议结束后回到 hard-task
  流水线（需求→方案→评审→实现→测试→交付）。
- 会议期间如需了解现状，可用 `ReadFile` 读取相关文件辅助判断，但**不得修改**。

## 注意事项

- 若 leader 会议消息未明确"只讨论"，成员应**默认先讨论、不落地**，并可在回复中确认：
  "已收到会议议题，以下为方案建议，待确认后再执行。"
- 禁止把"收集方案"误当成"分配任务"：assign_task 只在定案之后使用。
- 会议超时/无结论时，leader 应主动收敛决策（给出默认方案），避免无限开会。
- 会议内容若涉及高危/破坏性操作，方案必须包含风险评估，落地前需用户确认。
