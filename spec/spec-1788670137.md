## 工作流（workflow）

1. 建 todo：定位错误文案出处 → 精读调用链相关文件 → 梳理谁调用谁/谁检查 → 复现条件分析 → 日志取证 → 输出报告 → 核验行号。
2. 错误文案定位：用 Python 脚本遍历目标目录搜索关键字（绕开可能不稳定的内置 grep），记录 文件:行。
3. 调用链梳理：从工具入口（execute）逐层向下到 IO/传输层；对每个分支（成功/超时/异常/注销）标注代码行。
4. 日志取证：只读 app.log 等日志，按关键字扫描 + 时间线上下文（前后 100 行），寻找实际发生记录的锚点（WARNING/ERROR 行）。
5. 量化验证：规模/耗时类论断用只读脚本量化（文件数、大小、超时参数），不做破坏性测试。
6. 报告要点：出处（文件:行）、调用链、根因与复现条件、修复建议（改哪个文件哪处+风险）、证据清单、遗留疑点明确标注"不确定"。
7. 行号核验：报告引用行号必须用脚本回验，避免凭记忆。

## 该类任务规范

- 只读原则：不修改被诊断目录（如 server/）任何文件，不杀进程，不做破坏性操作；需要验证时只运行 python 检查/只读脚本。
- 先证后断：每个结论必须有代码行/日志行实证；无证据处标注"不确定"。
- 报告产出 UTF-8 Markdown，存 .output/ 下；临时脚本也放 .output/ 便于复现。
- 行号引用必须用脚本核验（read 或 python 锚点扫描），不得凭记忆写行号。

## 注意事项

典型场景：工具报错、连接不稳定、超时/注销类问题。常见陷阱：错误文案可能被上层二次包装（如 "本地执行器错误: 本地执行器已注销"），定位时先搜原始字符串再向上追踪包装点；日志取证优先找 WARNING/ERROR 行并建立时间线。
