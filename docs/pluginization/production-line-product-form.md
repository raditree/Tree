## 1. 一句话定位

**生产线是一个「只做决定」的工作台：用户每天花 20 分钟分发任务、回答必须由人回答的问题、
看产出；其余时间它自己按队列推进，并把每一次自动决定记在台账里。**

它不是聊天界面，也不是任务管理器的换皮：它把「准备 → 执行 → 复盘」固定成一条流水线，
用户只在三个位置出现：**拍板、处理异常、验收产物**。

### 1.1 核心差异：先摘要关键词 → 双查询图谱检索 → 一次 LLM 进入语义对齐

**传统 Agent 是「边聊边查」：先问一句，再翻文件、读文档、猜影响面，理解要几轮对话才成形。**
生产线的差异在需求提交后的第一屏：

> **先用一次 LLM 把需求与附件总结成「要求 + 关键词」→ 用原文与关键词做两次图谱检索
> （两次 embed 合计 ≤5s）→ 拼装上下文包 → 再一次 LLM 直接产出理解与首轮问题，进入语义对齐。**

- **先摘要，再检索**：无论有没有附件，都先调一次 LLM 总结用户要求、附件内容与关键词；
  避免拿附件原文/图片硬塞进检索，导致召回跑偏。
- **双查询是门控**：同一检索阶段跑两次查询——需求原文 + 关键词；两次 embed 合计 ≤5s，
  结果用 RRF 合并去重；不补第三轮检索，缺口交给 LLM 提问。
- **两次 LLM 分工**：LLM #1 只做摘要/关键词/附件总结；LLM #2 只做理解与语义对齐。
  两次耗时都单独计时，不混入检索 SLO。
- **证据先于结论**：LLM #2 只能引用上下文包里的 `evidence_id`；没有证据的结论自动降为「未知」。
- **10s 放宽为「检索阶段」**：摘要 LLM 与理解 LLM 单独计时；检索阶段（两次 embed + 图谱合并 +
  上下文包）P95 ≤10s，其中两次 embed ≤5s。
- 后面的打包/执行与传统 Agent 差异不大，**「先摘要、双查询召回、再一次 LLM 进对齐」才是产线的护城河**。

### 1.2 六条设计原则

| # | 原则 | 落到界面 |
| --- | --- | --- |
| 1 | **决定优先** | 默认页先列「待你决定」，再列异常、在跑、刚完成；不先展示全部任务 |
| 2 | **不聊天** | 没有输入框式对话；交互只有表单、问题卡、按钮与报告 |
| 3 | **失败可见** | 任何 `blocked` 必须在首屏出现，带原因、对应 run 与下一步动作 |
| 4 | **安全默认** | 写域、禁区、预算、并行、重试默认收紧；危险动作要显式确认 |
| 5 | **事实在盘上** | UI 只投影 `task.yaml / runs / inbox`；刷新/重连以磁盘状态为准 |
| 6 | **可回退** | 暂停、恢复、取消、重试都在界面上；不要求用户改 YAML 或敲命令 |

### 1.3 护城河：不是图谱，是「可执行、可约束、可验证、可追溯」的交付契约

图谱查询被做成插件工具给 Agent 调用，是好事——**检索会变成商品，不应该当护城河**。
如果只卖「查得准」，Agent + 工具 + 工作流很快能覆盖；打包/执行同样可复制。产线真正守的是下面几层：

| 层 | 产线负责 | 为什么 Agent + 图谱工具 + 工作流不够 |
| --- | --- | --- |
| **契约** | 需求五栏 → 理解卡 → 未答问题 → 范围/计划/验收落成磁盘 artifact | 工作流是提示词约定，模型可以跳过；产线「未答不落档」是硬判据 |
| **边界** | 写域、依赖、并行、租约、禁区；后端逐条校验 | Agent 靠自觉遵守提示词；产线不信任模型自述，越界直接拒绝 |
| **验证** | 独立门控命令、证据、`done` 定义 | 模型可以「说」跑过测试；产线只认门控输出与退出码 |
| **状态** | `task.yaml / runs / inbox` 持久化，崩溃/换模型/换 Agent 可续 | Agent 会话是临时的；断了就丢，工作流也救不回来 |
| **审计** | run 台账、pack 快照、`memory_hash`、决策记录 | 聊天记录不可回放、不可对账；产线能回答「当时为什么这么判」 |
| **协作** | 共享产线、门控模板、项目契约、决策历史 | 个人 Agent 会话无法成为团队的系统记录 |
| **可替换** | 契约在盘上，模型/Agent 只是执行者 | 换模型就重来；产线换执行者不换契约 |

一句话：

> **产线卖的不是「更聪明的检索」，而是「一个任务说 done 时，它真的按约定做完、且能证明」。**

- **不是护城河**：图谱查询、提示词、打包/执行、聊天式 UI、单次任务编排。
- **是护城河**：契约的不可跳过、边界的后端强制、验证的独立性、状态的持久性、审计的可回放，
  以及这些在团队/多任务/长时间跨度上的组合。
- **产品策略**：主动把图谱查询开放成插件工具，让 Agent 也能用；产线退到「系统记录 + 约束执行 +
  独立验收」层，竞争点从「谁查得准」转到「谁的 done 可信」。

### 1.4 稳定性怎么保证：控制面在企业侧，不在模型里

**「Agent 也能写域、也能回溯、也能并行、也能多 Agent 互审」是能力，不是保证。**
企业级稳定买的是**失败时的行为**：模型被提示注入、幻觉、超时、崩溃、换版本时，
系统仍然不越界、不丢状态、不假 done、可恢复、可审计。

| 能力 | 常见 Agent 做法 | 产线要给的保证 |
| --- | --- | --- |
| 写域 | 提示词 / 工具参数约束 | 执行站强制 + 租约 fencing；越界写直接拒绝，不靠模型自觉 |
| 回溯 | 会话历史 | append-only 事件日志 + 投影；崩溃后按事件重建，不靠聊天记录 |
| 并行 | 多 Agent 同时跑 | 写域冲突检测 + 串行/分支隔离；先防冲突，再谈并行 |
| 门控 | 审查 Agent 判断 | 独立门控进程 + 退出码/证据；执行者不能自签 `done` |
| 恢复 | 重试 / 重新开会话 | 幂等命令 + 租约 + 对账；断点续跑不重复写、不写半套 |
| 审计 | 聊天记录 | 不可变台账 + 证据链 + 决策快照；可回放「当时为什么这么判」 |
| 升级 | 换模型重测 | 契约测试 + 黄金任务 + 灰度/回滚；换模型不改变保证 |

七条硬机制：

1. **控制面与执行面分离**：状态机、门控、策略、预算在产线/核心；模型只是执行者。
2. **租约 + fencing token**：每个任务同一时刻只有一个有效执行者；旧 worker 的写请求带过期 token，直接拒绝。
3. **幂等命令 + 两阶段提交**：建任务、派发、写文件、门控都有幂等键；写范围在提交前校验，失败回滚。
4. **事件日志 + 投影 + 对账**：`task.yaml` 是投影，事件是源；崩溃后重放，定期对账磁盘实际状态。
5. **独立门控**：门控在隔离进程跑真实命令，记录命令/退出码/输出哈希；执行 Agent 不能修改门控结果。
6. **策略引擎外置**：写域、禁区、密钥、网络、工具权限在执行站判定；提示注入也改不了策略。
7. **故障注入 + 黄金任务 + SLO**：随机杀进程/断网/超时/部分写，验证可恢复；换模型跑黄金任务；
   对 `blocked/retry/恢复耗时` 设 SLO 与告警。

**为什么多 Agent 互审不够：**

- 审查者仍是模型，可能被同样的提示注入、上下文污染或错误证据带偏；两个模型一致不等于事实正确。
- 互审增加成本与延迟，但不产生**独立证据**。
- 正确分工：执行者不能自签；门控是确定性命令；高风险变更加人工四眼；Agent 审查只做辅助。

> **稳定性不是「Agent 更听话」，而是「即使 Agent 不听话、挂了、被换了，系统仍然守住边界，
> 并给出可验证的结果」。**

### 1.5 两条硬保证

| # | 保证 | 口径 |
| --- | --- | --- |
| G1 | **1 分钟内记录任务并理解需求** | T+0 任务落盘；T+60s 内出首版理解卡（允许 `partial`，但必须显示摘要/检索/模型三段进度与缺口）；慢模型不阻塞记录 |
| G2 | **仓库级迁移/重构不漂移、零漂移返工** | **原始需求逐条变成 `- [ ]` 门控**；**项目结构先理干净**（包单一职责、公共 API 少、无环/无重复/文档齐全）才开其他任务；先冻结基线/契约/不变量，再按可回滚切片迁移；每任务出口门禁 + 每批次漂移哨兵；**「零返工」定义为「不因语义漂移/上下文丢失而返工」**，真实新发现走变更单，不混入原任务 |

> G2 不是「一个出口门控」能保证的。门控只能证明“这一步过了”，防漂移要靠
> **基线 + 契约 + 不变量账本 + 变更分类 + 灰度迁移 + 追踪矩阵 + 漂移哨兵 + 回滚** 的组合（§5.4.3），
> 外加两条结构性前提：**原始需求逐条门控**、**项目结构干净（包职责单一）**。

## 2. 用户的一天（三个真实场景）

### 2.1 周一 20 分钟：分发

1. 打开产线 → 「今日」显示「还没有任务」→ 点「开始准备」。
2. 填需求五栏（目标/现状/验收/禁区/期限）→「开始理解」。
3. **10 秒内**上下文包就绪并自动发起 LLM；模型返回后出现理解卡：一句话理解、影响面、
   既有实现、约定、风险、未知与 3 个待拍板问题。
4. 直接逐条回答（每题有推荐项与不选后果）→「全部按推荐」。
5. 看范围与任务计划，改一条写域 →「确认并落档」。
6. 摘要出现：3 个任务、2 个可并行、门控命令 `dart analyze` →「开始执行」。
7. 关掉窗口。产线自己跑。

### 2.2 周三 5 分钟：处理异常

1. 打开产线 → 首屏「需要处理」：`T7 已阻塞 · 门控失败`。
2. 点开详情 → 「执行与门控」看到 2 个 analyze 错误 →「重试」。
3. 回到「今日」，任务重新进入 `running`；关窗口。

### 2.3 周五 5 分钟：验收

1. 打开产线 →「刚完成」列出 3 个 `done`，每条带门控结果。
2. 点「产物」→ 打开 `acceptance.md` 与 `pack.md`（落到文件窗）。
3. 看台账：token、耗时、每次决策动作；关窗口。

## 4. 工作台骨架

### 4.1 产线头（永远可见）

```text
┌ 标准开发流 · E:/work/project                         [配置] [暂停/恢复] [立即决策] ┐
│ 执行中 · 3/8 完成 · 预算 12.4k/100k · 主控：10:32 continue · 连续失败 0            │
└──────────────────────────────────────────────────────────────────────────────────┘
```

| 元素 | 口径 |
| --- | --- |
| 状态 | 后端计算：`初始化中 / 准备中 / 执行中 / 空闲 / 已暂停`；`需要你` 是叠加徽标，不写盘 |
| 进度 | `done / 非 cancelled 总数`；准备阶段显示「第 2 步 / 4」；初始化阶段显示「索引 3/4」 |
| 预算 | 用量 / 上限；未设上限显示「不限」；到点后变红并显示「已软停」 |
| 主控 | 最近一次动作与时间；`连续失败 > 0` 时变黄，`paused` 时显示原因 |
| 动作 | 配置、暂停/恢复、立即决策；初始化未完成时全部开任务动作禁用 |

#### 4.1.1 前置阻塞项（就绪门）

**在「项目结构整理完成 + 文档归一化完成 + 索引构建完成」之前，不得开任何任务。** 这是产线级硬门，不是提示。

| 检查项 | 完成判据 | 未完成时 |
| --- | --- | --- |
| **项目结构整理** | 结构报告就绪：包职责映射、公共 API 清单、依赖无环、重复实现已分类、大文件/TODO/文档缺口已分类；high 项为 0 或已显式豁免 | 阻塞；**只允许 `cleanup` 任务**，其他任务全禁 |
| 文档归一化 | `docnorm` 的 `doc_state` 已生成、归一化产物落盘；无文档时由 docnorm 明确标 `no_docs` | 阻塞，显示归一化进度 |
| 包图 | `pkg_index` 就绪且 `stale=false` | 阻塞，显示扫描进度 |
| 文档图 | `graph_*` 就绪且与 `doc_state` 指纹一致 | 阻塞，显示重建进度 |
| 代码索引 | `dedup_chunks / dedup_vectors` 就绪且与 `baseline_sha` 一致 | 阻塞，显示增量构建进度 |
| 测试映射 | `test/` ↔ `lib/` 映射已生成 | 阻塞 |
| 产线状态 | `line.ready=true`，`graph_version` 已固定 | 阻塞 |

规则：

- 未就绪时后端拒绝：`understand / task.create / task.attach / queue.dispatch / start / tick(新任务)`，
  统一返回 `409 line_not_ready`，带 `missing[]` 与 `progress`；**不提供 force/跳过开关**。
- 已经开跑的任务允许跑完当前 run，但**不得再开新任务**；产线头显示「索引重建中，已暂停开新任务」。
- 工作空间 HEAD 变化或索引变 stale 时，就绪门自动失效，重新构建完成后才恢复；不拿旧索引开新任务。
- 无 embedding 模型时，按已配置的 lexical 索引判定「构建完成」，标 `degraded: lexical`，但不算未就绪。
- UI 只是镜像：按钮禁用 + 清单 + 进度 + 「重新检测」；判据始终在后端。

```text
┌ 初始化产线 · 4 项完成 3 项 ─────────────────────────────── [重新检测] ┐
│ ✓ 文档归一化（12 篇）  ✓ 包图（42 包）   ✓ 文档图（1,204 块）         │
│ ◐ 代码索引（68% · 增量 96/142 文件）   ○ 测试映射                     │
│ 完成后才能开始理解、新建任务或执行；已运行任务会跑完当前一轮。          │
└───────────────────────────────────────────────────────────────────────┘
```

#### 4.1.2 文档归一化会改既有文档：按「预检写入」处理

文档归一化不是只读检查，它会**追加章节/索引行**，整篇改写还可能覆盖正文。所以它不能藏在
「开始理解」里顺手做，必须是一个可见、可审、可回滚的初始化写入阶段：

1. **先预览**：`docnorm` 以 `commit=false` 出计划，展示每个文件的 unified diff、
   动作（`append_section` / `append_index` / `rewrite`）、`skipped` / `rejected`；此步 0 写盘。
2. **再确认**：用户看 diff 后点「应用归一化」；`rewrite` 必须单独确认且在 `rewrite_allowlist` 内。
3. **写前保护**：记录目标文件 `before_sha256`，生成 `normalization/<runId>/` 备份/补丁；
   只允许追加，不允许凭空新建文档；路径限定在文档契约集合内，拒绝越界/符号链接。
4. **串行应用**：归一化期间产线 `初始化中`，任务全禁；写失败立即回滚，不留半套文档。
5. **幂等**：已有 heading / 索引行跳过；重复执行 0 写盘。
6. **重算索引**：写完重算 `doc_state`、文档图、包图与代码索引；`graph_version` 必须包含
   **文档内容 hash**，不能只看 git HEAD（归一化可能未提交）。
7. **可回滚**：保留备份/补丁与运行记录；一键回滚后产线重新阻塞，直到重新归一化并重建完成。
8. **不自动 commit**：默认只写工作区 + 产线资产补丁，不替用户提交；`allow_git_write=false` 时绝不提交。

```text
┌ 归一化预览：3 文件 / +18 −0 行 / 2 处整篇改写需确认 ──────────────── [取消] ┐
│ docs/architecture.md      append_section  ## 部署与回滚              [查看 diff] │
│ docs/known-issues.md      append_index    - #52 …                    [查看 diff] │
│ docs/README.md            rewrite ⚠ 需 allowlist                     [查看 diff] │
│ [应用并重建索引]   应用期间将暂停开新任务；失败自动回滚。                    │
└──────────────────────────────────────────────────────────────────────────────┘
```

#### 4.1.3 项目整理硬前置：结构不干净，不开其他任务

**取舍：牺牲灵活性，换稳定。** 包职责混杂、公共 API 泛滥时，任何迁移都会跨边界；
门控再多也挡不住语义漂移。所以项目整理必须是硬前置，不是建议。

现有 `audit`（文档/TODO/重复/大文件）只是报告，要升级为**结构门**：

**结构报告必须包含：**

| 项 | 内容 | 通过判据 |
| --- | --- | --- |
| 包职责映射 | 每个包一句职责、入口、公共 API、依赖 | 覆盖全部包；单包单一职责 |
| 公共 API 清单 | 导出符号/类型/接口；标记新增/变更 | 冻结；变更需 `DEC-xx` |
| 依赖结构 | 包依赖图、环、分层违规、跨包私有引用 | 环 = 0；分层违规 = 0 |
| 重复实现 | 相似代码块/重复包 | 已合并或登记为 known debt |
| 规模热点 | 超大文件/函数 | 已拆分或登记 |
| 文档缺口 | 包 README/契约缺失 | 已补或登记 |
| TODO/风险 | TODO/FIXME/known-issues | 已分类，不要求清零 |

**阶段与门控：**

```text
organizing（只允许 cleanup 任务）
→ normalizing（文档归一化）
→ indexing（包图/文档图/代码索引/测试映射）
→ ready（其他任务才可开）
```

- `organizing` 期间：`understand` 只对 cleanup 任务开放；`task.create/task.attach/queue.dispatch/start/tick`
  对非 cleanup 任务返回 `409 structure_not_ready`，带 `missing[]`。
- cleanup 任务同样是正式任务：有写域、门控、验收、回滚；跑完重新审计，不能“改完就算”。
- 结构报告 high 项为 0 才放行；确实要接受的，必须**逐项豁免**（owner + 原因 + 到期时间），
  没有全局跳过开关，豁免在首屏可见。
- 结构清理本身可能改动包边界/公共 API，因此必须在文档归一化与索引构建**之前**完成，避免索引反复失效。

**结构不变量（迁移时必须守住）：**

- `PKG-xx`：包 X 只负责某功能，只暴露列出的 API；
- `API-xx`：公共 API 集合冻结，新增/删除/改签名需 DEC；
- `DEP-xx`：包依赖图不新增环/不跨层；
- `SIZE-xx`：单文件/单函数不超过预算。

迁移任务若改变上述任一项，必须单列 `DEC-xx` 与对应门禁，不能“顺手重构”。

## 5. 准备阶段（需求 → 摘要 → 双查询检索 → LLM 理解 → 对齐 → 计划）

```text
[1 需求] ── [2 理解：LLM #1 摘要 → 双查询检索（10s）→ LLM #2] ── [3 对齐] ── [4 计划]
图谱：就绪（3 分钟前） · 覆盖 42 包 / 318 文件 / 1,204 文档块 / 96 代码块
窗口：本轮剩余 12:40（仅提示，可离开；未答跨日保留）
```

### 5.1 第 1 步：需求五栏

| 栏 | 必填 | 交互 |
| --- | --- | --- |
| 目标 | 是 | 单行；空泛词（优化/重构/差不多/尽快）给可点选改写建议 |
| 现状 | 否 | 多行 |
| 验收 | 是 | 多行；至少一条可判定标准 |
| 禁区 | 否 | 多行；默认继承 `policy.deny_globs`，只展示不改 |
| 期限 | 否 | 文本；不解析成时间，只作为提示 |

底部：`保存草稿`、`开始理解`。目标或验收为空时禁用并说明缺哪栏。
**就绪门未过时「开始理解」禁用**，悬停显示 `missing[]`（见 §4.1.1）；「保存草稿」可存，但不触达图谱/任务。

### 5.2 第 2 步：需求摘要 + 双查询图谱检索 + 一次 LLM

```text
需求五栏 + 附件
  → LLM #1：总结用户要求 + 附件内容 + 关键词          ← digest_ms 单独计
  → 双查询图谱检索：需求原文 embed + 关键词 embed       ← 两次 embed 合计 ≤5s
  → RRF 合并去重 + 包图 1 跳 + 变更/测试/风险
  → 上下文包（≤24k 字，带 evidence_id）                ← 检索阶段 10s 门控点
  → LLM #2：理解 + 首轮问题                            ← llm_ms 单独计
  → 语义对齐
```

#### 5.2.1 时限口径（10s 只约束检索阶段）

| 指标 | 口径 |
| --- | --- |
| **LLM #1 摘要** | 单独计时 `digest_ms`；目标 ≤20s，界面显示「正在总结要求/附件」；失败可重试或换模型，不静默跳过 |
| **两次 embed** | 原文查询 + 关键词查询，**合计 ≤5s**（单次超时按降级处理） |
| **检索阶段** | 两次 embed + 图谱合并 + 上下文包，**P50 ≤5s、P95 ≤10s** |
| **LLM #2 理解** | 单独计时 `llm_ms`，不计入检索 10s；卡面显示（如「模型 4.2s」） |
| **检索失败** | 到 10s 用已召回部分组包 + `partial/recall_gap`，仍然只调 LLM #2 |
| **模型** | 两次 LLM 都用 `roles.orchestrator.model_id`；`max_output_tokens ≤1 200`、temperature 0.1、JSON、**不给工具** |

预算拆解（只算检索阶段）：

| 阶段 | 目标 | 说明 |
| --- | --- | --- |
| 骨架渲染 | ≤0.2s | 回显需求 + 进度 |
| **两次 embed** | ≤5.0s | 原文查询 + 关键词查询，可并行；各带超时 |
| 双查询图谱检索 + RRF 合并 | ≤3.0s | 文档/代码 top-k、包图 1 跳、变更/测试/风险 |
| 上下文包拼装 | ≤1.5s | 去重、排序、裁剪到 24k、分配 `evidence_id` |
| 召回门控 + 状态渲染 | ≤0.3s | 检查覆盖、生成 `gaps`、显示「上下文已就绪」 |
| **合计** | **≤10s** | LLM #1 与 LLM #2 都不在此表 |

> 界面分三段显示：`摘要 8.2s · 检索 3.4s · 模型 4.2s`；
> 摘要慢不会拖累检索预算，检索慢也不会被误判成模型慢。

#### 5.2.2 LLM #1：需求摘要与关键词（无论有没有附件都必跑）

输入：需求五栏 + 附件清单（文本正文、图片本体、PDF/Office 元数据）。
输出严格 JSON，控制在 2k 字内：

```jsonc
{
  "requirement_summary": "一句话说清用户要什么、边界是什么",
  "keywords": {
    "terms": ["会话列表", "项目过滤"],
    "synonyms": ["session list", "project filter"],
    "entities": ["AgentList", "projectId"],
    "files": ["lib/ui/widgets/agent_list.dart"],
    "apis": ["SessionFilter"]
  },
  "constraints": ["不改数据库", "保持现有关键盘位"],
  "acceptance_signals": ["按项目过滤后列表实时变化"],
  "attachment_summaries": [
    {"id": "A1", "summary": "左栏设计稿：项目下拉在顶部，列表按分组折叠", "keywords": ["左栏", "项目下拉", "分组"], "status": "vision"},
    {"id": "A2", "summary": "接口文档：/sessions?project_id=", "keywords": ["project_id", "sessions"], "status": "text"},
    {"id": "A3", "summary": "PDF 仅元数据", "keywords": [], "status": "metadata_only"}
  ],
  "ambiguities": ["过滤状态是否持久化未说明"]
}
```

- **无论有没有附件都跑**：没有附件时只输出需求摘要、关键词与歧义。
- 图片由视觉模型总结；非视觉模型标 `manual`，提示用户补文字，不伪造。
- 文本附件总结并提关键词；PDF/Office 只给元数据（known-issues #51）。
- 失败处理：重试/换模型；如启用规则兜底，必须标 `digest_fallback`，关键词只能来自原文，
  不得凭空生成附件内容。

#### 5.2.3 双查询图谱检索（硬门控）

**同一检索阶段跑两次查询，不补第三轮。** 查询不是附件原文，而是 LLM #1 的产物：

- **查询 A（原文）**：目标 + 现状 + 验收 + 禁区，保留用户原始意图；
- **查询 B（关键词）**：`terms / synonyms / entities / files / apis` + 附件摘要关键词，
  补同义词、文件/接口名与设计稿里的说法。

两次 embed 合计 ≤5s（可并行，各带超时）；两路各自检索后用 RRF 合并去重，
再补包图 1 跳、变更/测试/风险。一次召回六类图谱上下文：

| 维度 | 来源 | 配额（默认） |
| --- | --- | --- |
| 包/入口/依赖 | `docnorm.scan` 的 `pkg_index` | 8 包 / 12 入口 |
| 文档约定 | `docnorm` GraphRAG chunk + 社区报告 | 12 段 |
| 相似实现 | `dedup_chunks / dedup_vectors` top-k | 8 块 |
| 变更上下文 | `git status` + 近期 `git log` | 20 文件 |
| 测试关联 | `test/` ↔ `lib/` 路径映射 | 10 文件 |
| 风险与未知 | known-issues / TODO / `deny_globs` / 写域交叠 | 10 条 |
| **附件关键词** | LLM #1 的 `attachment_summaries[].keywords` | 直接进查询 B，不读附件原文 |

**召回门控（recall gate）**：

- 两路查询都要有贡献；某一路为空/失败 ⇒ 标 `degraded: single_query`，不静默只用一路。
- 至少命中 1 个包、1 个代码块、1 段文档、1 条测试或风险；否则标 `recall_gap`。
- 附件本身不算项目维度：附件读不了只进 `gaps`，不冒充「已理解」。
- 相似度低于阈值的条目不硬塞；缺哪个维度就写进 `gaps`。
- `recall_gap` **不触发第三次检索**；把缺口原样交给 LLM #2，让它变成「未知」或提问。
- 无 embedding 模型时降级 lexical，并标 `degraded: lexical`。

#### 5.2.4 上下文包（LLM #2 的唯一输入）

```jsonc
{
  "requirement": {"goal": "...", "current": "...", "acceptance": "...", "forbidden": "...", "deadline": "..."},
  "digest": {
    "requirement_summary": "一句话总结",
    "keywords": {"terms": [], "synonyms": [], "entities": [], "files": [], "apis": []},
    "constraints": [],
    "acceptance_signals": [],
    "ambiguities": []
  },
  "graph": {"version": "...", "fresh": true, "coverage": {"packages": 42, "files": 318, "docs": 1204, "chunks": 96}},
  "evidence": [
    {"id": "E1", "kind": "doc|code|package|change|test|risk|attachment", "path": "lib/...", "line": 88, "snippet": "...", "score": 0.82}
  ],
  "attachment_summaries": [
    {"id": "A1", "evidence_id": "E20", "name": "design.png", "summary": "左栏设计稿：顶部项目下拉、分组折叠",
     "keywords": ["左栏", "项目下拉", "分组"], "status": "vision", "mime": "image/png", "size": 245760}
  ],
  "gaps": ["没有找到相关测试", "项目未启用 embedding", "A3 PDF 仅存不可读"],
  "limits": {"max_questions": 3, "max_images": 4}
}
```

- 上下文包的主体是 **LLM #1 的摘要/关键词** + 双查询召回的 evidence，不是附件原文。
- 图片已在 LLM #1 总结；包内只放摘要与元数据，**不放 base64**。LLM #2 默认读摘要，
  必要时才附带 ≤4 张 image part（视觉模型且预算内）。
- 文本附件在 LLM #1 已总结；包内只放摘要与关键词，不重复塞全文。
- 超出 24k 字按「文档 / 代码 / 附件摘要 / 风险」优先级裁剪，裁剪项进 `gaps`。
- 同一份上下文包可复用于重试；**重试不重新摘要/检索**，除非用户点「重新理解」。

#### 5.2.5 LLM #2：理解 + 语义对齐

上下文包就绪后立即发起 LLM #2；模型耗时单独记录为 `llm_ms`，不计入检索 10s。

系统提示词固定四段：角色（产线主控）、事实（上下文包）、边界（证据规则/提问规则）、
输出契约（严格 JSON）。**不提供工具、不做多轮。**

- 图片已在 LLM #1 总结；LLM #2 默认只读摘要。
  仅当需要核对视觉细节、模型支持视觉且预算允许时，附带 ≤4 张 image part，不额外 OCR。
- 模型不支持视觉：只读摘要，`gaps` 记 `image_manual_reference`，提示用户补文字说明。
- 图片 part 受 token/字节预算约束；超限不送，摘要仍保留。

输出：

```jsonc
{
  "understanding": "一句话理解",
  "impact": [{"text": "...", "evidence_ids": ["E1"]}],
  "reuse": [{"text": "...", "evidence_ids": ["E4"]}],
  "conventions": [{"text": "...", "evidence_ids": ["E2"]}],
  "risks": [{"text": "...", "evidence_ids": ["E7"]}],
  "unknowns": ["..."],
  "questions": [{"text": "...", "default": "...", "recommended": "...", "consequence": "..."}],
  "evidence_used": ["E1", "E2", "E7"]
}
```

**证据校验（服务端）**：

- 每条 `impact/reuse/conventions/risks` 必须引用存在的 `evidence_id`；
  引用不存在或没引用 ⇒ 该项移入 `unknowns`，不展示为结论。
- `questions` 最多 N 条（设置默认 3），超出截断并显示计数。
- 校验失败不重试第二轮；整份理解标 `invalid_evidence`，让用户重试或换模型。

- 没有证据的条目只出现在「未知」，不进入结论区。
- 卡面直接可回答首轮问题，不需要再点「进入对齐」加载。

#### 5.2.7 覆盖与「真实全面」

「全面」= 六维覆盖 + **双查询门控** + 附件摘要覆盖 + 证据校验，不是读完全部代码：

| 维度 | 卡片呈现 | 不满足时 |
| --- | --- | --- |
| 代码结构 | 影响包、入口符号 | 进 `gaps`，问范围 |
| 相似实现 | top-k 相似块 + `path:line` | 进 `gaps`，不猜 |
| 文档约定 | 相关章节/决策 | 进 `gaps` |
| 变更上下文 | 已改文件、近期同区工作 | 标 stale |
| 测试关联 | 可能受影响的测试 | 进 `gaps` |
| 风险与未知 | 风险条目 + 显式未知 | 至少列 1 条风险/未知 |
| 附件摘要 | 附件数 / 已总结 / 不可读 / 仅元数据 | 不可读进 `gaps`，不伪造 |

底部固定显示覆盖读数：`包 42 / 文件 318 / 文档块 1,204 / 代码块 96 / 附件 3（2 已总结） / 未覆盖 7`。
双查询未合并前不展示；某一路失败标 `degraded: single_query`。

#### 5.2.8 新鲜度、预 warm 与缓存

- 建线 / 选中产线 / 工作空间变化时后台建索引；提交需求优先读缓存。
- 缓存键 = `requirementHash + digestHash + graphVersion + modelId + promptVersion`；
  命中直接回理解卡，**0 次摘要/0 次检索/0 次模型调用**；点「重新理解」绕过缓存。
- 索引 stale 时仍可用，卡片标黄并显示变更文件数。

#### 5.2.9 超时、降级与重新理解

- **LLM #1 摘要超时/失败**：显示「总结要求失败」；可重试或换模型；如启用规则兜底必须标
  `digest_fallback`，关键词只能来自原文，不得生成附件内容。
- **embed 超时**：两路查询各自有超时；一路失败 ⇒ 标 `degraded: single_query`，
  用另一路继续，不补第三次 embed。
- **检索到 10s 未完成**：中止检索，用已召回部分组包并标 `partial/recall_gap`；
  **仍然只调 LLM #2**，缺口交给它变成「未知」或提问。
- **LLM #2 超时/不可用**：显示上下文包摘要与模型错误；可「重试」（复用同一上下文包与摘要，
  不再检索）或「重新理解」（重跑摘要 + 双查询 + LLM #2）。LLM #2 耗时单独展示。
- **检索门控不过**：标 `recall_gap`，缺哪个维度写进 `gaps`；不补第三轮。
- **重新理解**：重跑 LLM #1 + 双查询 + LLM #2，生成新的 `understanding_id`；旧卡保留可对比。
- **不做后台深化**：双查询就是门控；需要更多上下文时由用户点「重新理解」。

#### 5.2.10 附件摘要与图片边界

**原则：附件先由 LLM #1 总结成「内容摘要 + 关键词」，再参与检索；附件原文/图片不直接进图谱；
二进制不塞进上下文包。**

流程：

1. **校验**：`realpath` 必须落在 `.input/production_lines/<line>/tasks/<task>/attachments/`；
   MIME 按字节嗅探，不信任扩展名；`sha256` 必须与登记一致；大小/数量受限。
2. **分类**：
   - 文本/代码/Markdown/JSON/CSV：读 ≤4k/个交给 LLM #1 总结，产出摘要与关键词；
   - 图片：元数据 + 图片本体交给 LLM #1（视觉模型）总结；
   - PDF/Office/其它二进制：只元数据 + `unreadable` / `manual_only` gap（known-issues #51）。
3. **图片预处理**（目标 ≤1s；超时降级为元数据）：
   - 解码前查像素上限（防解压炸弹），超限拒绝或降采样；
   - 应用 EXIF orientation，剥离 EXIF/GPS，转 sRGB；
   - 长边缩到 360–1024；最多 4 张、总计 ≤12MB；按附件顺序取前 4，其余进 `gaps`；
   - 动图取首帧并标 `animated`；透明图转 JPEG 时合成白底，PNG 保留透明；
   - SVG 按 XML 提取标题/`<text>`，必要时栅格化；禁止脚本与外部引用；
   - HEIC/RAW/TIFF/BMP：有解码器则转 PNG，否则 `metadata_only`；
   - PSD/Sketch/Figma/AI：只存；有内嵌预览则取预览，否则 `manual_only`；
   - 相同 `sha256` 去重：一个 evidence，多个文件名；
   - 损坏/空白/过小（<64px）：`unreadable` / `low_information`，不伪造描述。
4. **LLM #1 总结**：每个附件产出 `summary` + `keywords` + `status`；图片由视觉模型读，
   每张图带 `image_label` 与 `evidence_id`；关键词并入查询 B。
5. **非视觉模型**：图片标 `manual`，`gaps` 记 `image_manual_reference`，UI 提示「请补文字说明」；
   不静默忽略、不伪造。
6. **失败不阻塞理解**：附件读不了只进 `gaps`；但若验收依赖该附件，派发前预检阻断。
7. **安全**：不把 base64 写进上下文包/日志；不外部下载；不执行 SVG 脚本；v1 不做 OCR，
   图片里的文字只由视觉模型在 LLM #1 读取。

| 边界 | 处理 | 结果 |
| --- | --- | --- |
| 超大图（>40MP / >20000px） | 像素上限保护，拒绝或降采样 | `resized` / `rejected` |
| 动图 GIF/WebP | 取首帧 | `animated: true` |
| 透明 PNG | 保留透明；转 JPEG 时白底 | 正常读 |
| EXIF 旋转 / GPS | 应用方向、剥离 GPS | 正常读，隐私保护 |
| 损坏 / 截断 | 解码失败 | `unreadable`，进 `gaps` |
| 扩展名与内容不符 | MIME 嗅探 | 按真实类型处理或拒绝 |
| 符号链接 / 路径穿越 | 真实路径校验 | 拒绝 |
| 重复图片 | sha256 去重 | 一个 evidence，多文件名 |
| 超过 4 张 | 取前 4，其余元数据 | 其余进 `gaps` |
| 单文件 >20MB / 任务 >50MB | 预检拒绝 | `attachment_too_large` |
| SVG 外部引用/脚本 | 禁止加载与执行 | 只取本地文本 |
| 加密 PDF | 无法预览/抽取 | `unreadable` |
| 截图里的文字（非视觉模型） | 不 OCR | `image_manual_reference` |

### 5.3 第 3 步：对齐

每个 `Q` 一张卡：

```text
Q1 验收以哪份文档为准？                     [默认 A] [推荐 A]
A. docs/project-status.md
B. docs/work-log.md
不选后果：将按 A 执行，索引可能缺少历史口径。
[选择 A] [选择 B] [其它…]
```

- 一次最多 N 条（设置默认 3），超出截断并显示「还有 N 条未展示」。
- 首轮问题由这次 LLM 直接生成，在理解卡里就能回答；「重新理解」生成的新问题进入下一轮。
- `全部按推荐` 只对准备阶段问题生效，必须用户点击。
- 有未答问题时，第 4 步「确认并落档」置灰，并显示还差哪几题。
- 离开页面不丢；窗口关闭后任务转 `awaiting_user`，下次继续。

### 5.4 第 4 步：计划与落档

```text

任务计划

T2 会话列表测试         依赖 T1   写域 test/                            验收 dart test
T3 左栏过滤交互         依赖 T1   写域 lib/ui/widgets/agent_list.dart   验收 dart test
T4 集成验收             依赖 T2/T3 写域 -                              验收 dart test + 手工场景
方案设计：strangler + adapter · 兼容窗口 2 周 · 回滚点 S3
不变量：API-01 / DB-02 / PERF-03（3 条，均有关联门禁）
出口门禁：T1 9 项 · T2 6 项 · T3 8 项 · T4 端到端 12 项

批次：B1 T1；B2 T2/T3（写域交叠，串行）；B3 T4
拆分检查：T2/T3 写域交叠 · T3 缺任务级门控 · 已补集成任务 T4
[编辑任务] [拆分/合并] [重新拆分] [删除] [新增任务]

```

- 任务行可编辑：标题、`task_type`、依赖、读写域、验收、门控；保存前跑拆分校验。
- 落档前预览将写入的项目资产清单（`recon/scope/plan/decisions/...`）。
- 落档后展示 ≤10 行分发摘要 + `开始执行`（或按拍板自动启动）。
- 落档后的任务与手建任务完全同构，后续可在「执行」里继续改计划字段。

#### 5.4.1 任务拆分协议：Task = 可独立验证的契约

**拆分目标不是「把活分小」，而是「每个任务都能独立验证、独立回滚、且能安全并行」。**

**任务字段**（在现有字段上扩展，保留旧任务兼容）：

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `id / title` | 是 | 唯一、可读 |
| `goal` | 是 | 一句话说明这个任务改变什么，不写“实现XX功能” |
| `task_type` | 是 | `code / test / docs / spike / integration / chore / cleanup`；与 `kind`（conventional/special）分开 |
| `depends_on` | 否 | **硬依赖**：没有它的产物就无法开始 |
| `conflicts_with` / `serial_group` | 否 | 软冲突：共享文件/注册表，不必有依赖，但不能并行 |
| `write_scope / read_scope` | 是/否 | 写域必须非空（集成/文档任务除外）；读域最小化 |
| `acceptance` | 是 | 行为判据；至少一条可判定 |
| `gate` | 是 | 命令/检查 + 期望；没有门控的任务不得 `done` |
| `estimated_files / changed_lines / minutes` | 否 | 用于拆分预算与批次估算 |
| `risk` | 否 | `low/medium/high`；高风险必须有人审或更严门控 |
| `contract` | 否 | 输入/输出/接口/不变量；跨任务协作靠它，不靠聊天 |
| `rationale` | 是 | 为什么这样拆，引用理解卡的 `evidence_id` |

**拆分规则：**

1. **一个任务 = 一个意图 + 一个写域 + 一个门控 + 一组验收**；四者缺一就拆或补。
2. **优先纵向切片**：每个任务尽量从入口到验证闭环；不要“先写所有 model，再写所有 UI”。
3. **尺寸预算**：目标 1–5 文件、≤300 改动行、≤1 个包、≤30 分钟 agent 时间；
   超过任一项提示拆分。
4. **必须拆**：跨 >2 个包、改 >1 个公共 API、混重构+新功能、无法独立验证。
5. **可以合**：同文件、同门控、总是一起改的任务，合并减少上下文切换。
6. **热文件单写**：注册表、导出、配置、路由等共享文件只归一个任务；其他任务通过 `conflicts_with`
   或集成任务处理，禁止并行写同一文件。
7. **集成任务**：多任务功能必须有 `integration` 任务，依赖所有代码任务，跑全量门控 + 端到端验收；
   没有它，单任务全绿 ≠ 功能可用。
8. **spike 有界**：只用于消除关键未知，限时、产出决策/证据，不写生产代码；结论回到计划再拆实现。
9. **文档任务显式**：需要改 README/work-log 时单独列 `docs` 任务，写域只含文档，串行执行。
10. **依赖只留硬的**：`depends_on` 只表示“缺它的产物就做不了”；“最好先做”用优先级/批次，不要造依赖链。

**依赖与批次：**

- 硬依赖 → 拓扑排序；同层按写域不相交分组，得到可并行批次。
- 写域相交 → 同批串行或拆文件；不用“多 Agent 并行”掩盖冲突。
- 批次受 `limits.max_parallel_tasks`、预算与租约约束；批次只是建议，执行前仍要过写域检查。

**流程（不是让模型一次说了算）：**

```text
LLM 起草 DAG（带 rationale/evidence）
→ 静态校验（schema/依赖/环/写域/尺寸/门控/集成任务）
→ 确定性修正（超限拆分、微任务合并、交叠串行、去伪依赖）
→ 用户审阅（拆分/合并/改依赖/改门控/锁定）
→ 落档（计划版本 v1）
```

- 校验失败不落档：环、跨计划依赖、写域交叠未处理、任务无门控、超大任务、缺集成任务。
- 落档后改计划 → 新版本 `plan-v2`；在途任务跑完当前 run，新任务按新版本。

**反模式：**

- 「实现 XX 功能」巨型任务；「先写测试后写代码」但无代码任务；按文件一人一个任务；
- 所有任务串成一条依赖链假装安全；用 `depends_on` 代替写域冲突处理；
- 多 Agent 并行写同一文件，再靠合并解决冲突。

#### 5.4.2 计划生成：多轮自我迭代，再给用户审查

LLM 一次生成无法回头改，所以计划必须**先写完，再分轮批判/修正**，不能指望“一次输出完美”。

```text
R1 起草：完整计划（设计/不变量/任务/门禁/追踪矩阵/风险）
R2 批判：独立调用，只出 findings（严重度 + 证据 + 修复建议），不改稿
R3 修正：按 findings 打补丁，重跑确定性校验
R4..N：重复批判/修正，最多 3 轮；无 high 或预算到即停
冻结：plan-vN 交用户审查（diff + 未解决 findings）
```

**计划必须包含 7 块：**

1. **方案设计**：现状 → 目标、架构/数据流、迁移策略、兼容窗口、回滚方案、被否决的替代方案。
2. **不变量账本**：行为/API/数据/权限/性能/UX 不变量，每条有 owner、检查方式、影响任务。
3. **任务拆分**：DAG + `goal/task_type/写域/依赖/冲突/预算/合同`（§5.4.1）。
4. **出口门禁**：每任务一份 `- [ ]` 清单（命令/期望/证据），见 §5.4.3。
5. **追踪矩阵**：需求/验收 → 设计决策 → 不变量 → 任务 → 门禁 → 证据，任一行断链即不落档。
6. **风险与未知**：高风险项、未决问题、需要人工拍板的决策。
7. **变更控制**：计划版本、变更单模板、回滚点。

**批判清单（每轮都跑）：**

- 每条需求/验收是否都有任务承接、有门禁证明？
- 每条不变量是否有检查；哪些任务会改变它，是否已批准？
- 是否有任务超尺寸、写域交叠、循环依赖、伪依赖？
- 迁移顺序是否可回滚；是否先有基线/契约冻结？
- 是否混了「保持行为不变的重构」与「改变行为的迁移」？
- 集成任务是否存在并覆盖端到端验收？
- 门禁是否可执行、是否只写了“测试通过”这种空话？
- 未决问题是否显式，而不是被计划默认？

**停止条件**：连续一轮无 `high` findings、确定性校验全过、追踪矩阵无断链；否则最多 3 轮后
带着未解决项交给用户，**不允许静默忽略**。

#### 5.4.3 大规模迁移/重构：防语义漂移

**语义漂移** = 实现逐渐偏离既定行为/契约/不变量，但每步门控都“绿”，直到最后才发现。
单靠出口门控防不住，因为门控只证明局部，不证明“没变味”。

**先做两件结构性的事：**

- **原始需求逐条编号 `REQ-xx`，每条至少对应一个 `- [ ]` 门控**；需求→门控断链不落档。
- **项目结构先理干净**：包单一职责、公共 API 少、无依赖环、重复/大文件/文档缺口已分类；
  结构不变量 `PKG/API/DEP/SIZE` 冻结（§4.1.3）。

**八层防线：**

| 层 | 做法 | 产出 |
| --- | --- | --- |
| 0. 结构基线 | 项目整理完成：包职责/API/依赖/重复/文档/规模；结构不变量冻结 | `structure.md` + `PKG/API/DEP/SIZE` |
| 1. 基线冻结 | 迁移前先补 characterization tests / golden corpus / API 契约 / schema 快照 / 事件 fixture，基线必须全绿并冻结 | `baseline-v1` + 覆盖报告 |
| 2. 契约冻结 | 公共 API、类型、DB schema、事件、错误码、配置、权限、UX 流程写成契约；改动必须走变更单 + 双人确认 | `contract.md` + `DEC-xx` |
| 3. 不变量账本 | 每条不变量有检查方式与 owner；任务声明 `preserves` / `changes` | `invariants.md` |
| 4. 变更分类 | **行为保持型重构**与**行为改变型迁移**分开任务；重构任务不改契约/输出；改变必须单独批准 | 任务 `task_type` + `change_kind` |
| 5. 增量迁移 | strangler / adapter / 新路径走 feature flag / 新旧并行 / 影子流量 / 双写对账；禁止大爆炸 | 可回滚切片 |
| 6. 追踪矩阵 | 每个 diff 必须能映射到任务/需求；无法映射的改动直接阻断 | `traceability.md` |
| 7. 漂移哨兵 | 每批次后自动比对：越界文件、API/schema diff、依赖图新增环/分层违规、golden 输出 diff、数据对账、文档漂移 | `drift-report` |

**迁移切片模板（每步都有出口门禁与回滚）：**

```text
S0 基线/契约冻结 → S1 引入抽象/适配层 → S2 新路径（flag off）
→ S3 新旧并行/影子对比 → S4 按范围切流 → S5 删除旧路径 → S6 文档/清理
```

**每任务出口门禁（`- [ ]` 清单，机器可解析）：**

```markdown
- [ ] `dart analyze` 退出码 0
- [ ] `dart test test/foo_test.dart` 全绿
- [ ] golden corpus 20/20，输出 diff = 0
- [ ] `git diff --name-only` ⊆ `write_scope`
- [ ] 公共 API diff = 0，或 `DEC-xx` 已批准
- [ ] schema checksum 未变，或迁移单已批准
- [ ] 依赖图无新增环/分层违规
- [ ] 回滚演练通过
- [ ] 文档更新（如需）已完成
```

**零返工的口径：**

- 目标是 **零「漂移返工」**：不因语义漂移、上下文丢失、计划漏项而重做。
- 真实新发现（外部约束变化、基线缺失）走**变更单**：影响分析 → 更新计划版本 → 重跑门禁，
  不计入原任务的返工率。
- 指标：`drift_events`、`scope_violations`、`contract_changes_without_DEC`、`first_pass_gate_rate`、
  `rework_rate`；每周看趋势，不靠感觉。

**不能自动化的部分**：UX 意图、命名、架构美感、业务取舍，无法完全用测试证明。
这些进**决策记录 + 人工评审**；一旦变更必须显式签字，不能让模型“顺手改”。

## 6. 执行阶段

### 6.0 任务输入与派发（手建任务）

**现状缺口**：UI 建任务只有「标题 + 写域」，没有任务内容、验收判据、依赖、附件与引用；
后端 `task.yaml` 已经有 `intake / acceptance / read_scope / depends_on`，但没有编辑契约与附件通道。
本节把「任务是什么」补成可执行输入，而不是只有一行标题。

#### 6.0.1 任务输入字段

| 字段 | 必填 | 用途 |
| --- | --- | --- |
| `title` | 是 | 列表与台账识别 |
| `brief` | 派发前必填（或 `intake.goal` 非空） | 任务内容 / 要求，Markdown；打包与执行提示词的第一段 |
| `acceptance` | 派发前至少 1 条 | 门控之外的人可读验收判据 |
| `write_scope` | 否 | 默认 `**`（整个工作空间，串行、禁区照拦） |
| `read_scope` | 否 | 参考范围；添加 `references` 时自动并入 |
| `references` | 否 | 工作空间内已有文件路径（不复制）；自动并入 `read_scope` |
| `attachments` | 否 | 上传到 `.input` 的只读输入（设计稿/文档/图片） |
| `depends_on` | 否 | 硬依赖；未 `done` 不派发 |
| `conflicts_with` / `serial_group` | 否 | 软冲突：共享文件/注册表，不能并行但不必有依赖 |
| `task_type` | 否 | `code / test / docs / spike / integration / chore / cleanup`，默认 `code`；与 `kind` 分开 |
| `gate` | 否 | 任务级门控命令/期望；缺省用产线默认门控；没有门控不得 `done` |
| `priority` | 否 | 默认 50；队列排序 |
| `kind` | 否 | `conventional / special`；影响提示词措辞 |
| `intake` | 否 | 准备阶段五栏；有值时作为「需求模板」只读展示并进入提示词 |

规则：

- `brief` 是手建任务的主输入；准备阶段落档的任务可以把 `plan.md` 的任务摘要写入 `brief`，
  同时保留 `intake` 作为背景。
- `acceptance` 与 `gate` 分开：前者给人看/给模型对齐，后者是真正跑的命令；
  没写 `gate` 时仍按 `pack.baseline` → `dart analyze` 兜底。
- 附件是**只读输入**，不参与写域判定，也不会被 `deny_globs` 拦截；写域只约束执行期改动。

#### 6.0.2 新建 / 编辑表单

```text
┌ 新建任务 · T3 ────────────────────────────────────────────────────────────────┐
│ 标题   [ 会话列表支持按项目过滤                                        ]        │
│ 内容   [ Markdown：要做什么、现状、边界……                    ] [预览]          │
│ 验收   [+ 添加判据]  · dart analyze 无新增  · 相关用例全绿                     │
│ 范围   写域 [ ** ]（默认整个工作空间）   读域 [ lib/ui/, lib/io/ ]             │
│ 依赖   [ T1 × ]  优先级 [50]  类型 [常规 ▾]                                    │
│ 附件   [上传文件] [引用工作区文件]                                              │
│        [🖼 design.png 240 KB ×] [📄 notes.md 12 KB ×] [📕 spec.pdf 1.2 MB ×]   │
│ 提示   图片需要打包/执行模型支持视觉；PDF/Office 首版仅存储与预览，不自动读取。   │
│                                        [保存草稿] [创建并加入队列] [创建并开始] │
└────────────────────────────────────────────────────────────────────────────────┘
```

- 内容用多行 Markdown；`预览` 复用现有 Markdown 渲染，不引入富文本编辑器。
- `创建并加入队列`：校验通过后建 `queued` 任务；产线开着自动推进时由下一次决策接手。
- `创建并开始`：建任务后立即触发一次「开始执行」（等价于切到执行页点一次）。
- `保存草稿`：建 `draft`，允许内容/验收不完整；补齐后才能入队。
- 附件支持选择本地文件、拖拽、粘贴截图；预览复用消息输入框的附件卡。

#### 6.0.3 附件支持矩阵

| 类型 | 预览 | 模型是否可读 | 首版口径 |
| --- | --- | --- | --- |
| Markdown / 文本 / 代码（md/txt/json/yaml/csv/dart/py/ts…） | 文本 | ✅ `read` 工具 | 完整支持；提示词只给路径与大小，不整篇塞入 |
| 图片（png/jpg/jpeg/webp/gif） | 缩略图 | ✅ 仅当角色模型支持视觉 | 走 `tree.agent` 现有 vision 通道；不支持时界面预检警告 |
| PDF | 现有 PDF 预览 | ❌ 首版不抽取正文 | 存储 + 预览；提示词标「不可直接读取」 |
| Office（docx/xlsx/pptx） | 否 | ❌ 首版不抽取正文 | 存储；提示词标「不可直接读取」 |
| 其它二进制 | 文件名/大小 | ❌ | 存储；提示词标「不可直接读取」 |

限制（v1 常量，后续可进 `limits`）：

- 单文件 ≤ 20 MB、单任务 ≤ 50 MB、最多 20 个附件；
- 只接受普通文件，拒绝目录、符号链接与工作空间外路径；
- 同名文件自动加 `-1/-2` 后缀，不覆盖已有附件；
- 图片内联沿用项目既有约束（长边 360–1024、单请求体上限），超限走引用而不是硬塞。
- **首版允许「只存不读」**：PDF/Office/其它二进制与非视觉模型下的图片只落盘与预览，
  不抽取正文、不伪造描述；该取舍登记为 known-issues #51，抽取能力后续单独立项。
- **理解阶段同矩阵**：先由 LLM #1 总结文本/图片（图片仅视觉模型），摘要与关键词进检索；
  非视觉模型标人工参考；读不了只进 `gaps`，不阻塞理解（验收依赖时派发前阻断）。边界见 §5.2.10。

#### 6.0.4 存储与上传流程

**存储位置**（工作空间 `.input`，不进项目资产、不随 git 提交；用户 2026-11-14 拍板）：

```text
<workspace>/.input/production_lines/<line_id>/tasks/<task_id>/attachments/<name>
```

`task.yaml.attachments` 记录元数据：

```yaml
attachments:
  - name: design.png
    path: .input/production_lines/pl_.../tasks/T3/attachments/design.png
    size: 245760
    type: png
    sha256: 9f2c...
    added_at: 2026-11-14T10:00:00+08:00
```

**上传流程**（不传二进制经产线插件，复用既有分片通道）：

1. UI 用现有 `uploadFileChunked` 把本地文件传到产线工作空间（files 插件 `line:<lineId>` 作用域），
   落点仍是 `.input/{yyyymmdd}/...`；拿到工作空间相对路径。
2. UI 调 `production.task.attach`（或建任务时带 `attachment_sources`），传 **工作空间相对路径**；
   插件校验来源必须在 `.input/` 或本线资产目录内。
3. 插件复制到 `.input/production_lines/<line>/tasks/<task>/attachments/`，计算 `sha256/size/type`，写回 `task.yaml`，
   删除 `.input/{yyyymmdd}/` 临时件；返回完整任务。
4. 失败（超限/越界/文件名非法）在表单内就地报错，已上传的临时件由插件清理。

> 不把本机绝对路径交给插件：即使当前是本地工作空间，也保持与 SSH 工作空间一致的
> 「先上传、再登记」口径，避免以后换远端执行时重做。

#### 6.0.5 派发前预检（UI 与后端同判据）

| 检查 | 不通过时 |
| --- | --- |
| 标题非空 | 禁止保存 |
| `brief` 或 `intake.goal` 非空 | 「任务还没有内容」 |
| `acceptance` ≥ 1 条 | 「至少写一条验收判据」 |
| 执行 Agent / 执行模型存在 | 「先配置执行 Agent 与模型」 |
| 工作空间存在且是 git 仓 | 警告：可打包，但无法判写域（执行会被拒） |
| 附件都存在且 `sha256` 一致 | 「附件已变化，请重新上传」 |
| 图片附件 + 模型无视觉 | 警告并要求确认「图片仅作人工参考」 |
| `depends_on` 未满足 / 写域交叠 / 并行满 | 不派发，给 `waiting_on` / `with_task` |

#### 6.0.6 提示词组成

打包与执行共用同一段任务输入（顺序固定）：

```text
任务：T3 会话列表支持按项目过滤
内容：
<brief>

需求模板（如有）：
目标 / 现状 / 验收 / 禁区 / 期限

验收判据：
- dart analyze 无新增
- 相关用例全绿

附件（只读）：
- [text] notes.md · 12 KB · docs/production_lines/.../notes.md（可用 read）
- [image] design.png · 240 KB · docs/production_lines/.../design.png（仅视觉模型）
- [binary] spec.pdf · 1.2 MB · docs/production_lines/.../spec.pdf（不可直接读取）

引用文件：
- docs/project-status.md
- lib/ui/widgets/agent_list.dart

项目文档（docs.memory_manifest 摘要）：
<projectContext>

记忆（agent.memory.get 返回，原样）：
<memory.text>

写域：lib/ui/widgets/agent_list.dart
读域：lib/ui/, docs/project-status.md
```

- 打包提示词带完整任务输入；执行提示词带同一段 + `pack.json` + `acceptance.md`。
- 执行期主控仍只看快照，不读附件正文；附件只影响打包/执行的提示词。
- `pack.json` 记录附件快照（`path + sha256`）；执行前校验，变了就拒跑并要求重打包。

#### 6.0.7 编辑边界

| 任务状态 | 可改内容/验收 | 可改附件/引用 | 可改范围/依赖 |
| --- | --- | --- | --- |
| `draft` | ✅ | ✅ | ✅ |
| `queued` / `blocked` / `awaiting_user` | ✅ | ✅ | ✅ |
| `packed` | ⚠️ 需重新打包 | ⚠️ 需重新打包 | ⚠️ 需重新打包 |
| `packing` / `running` / `gating` | ❌ | ❌ | 仅优先级/依赖 |
| `done` / `cancelled` | ❌ | ❌ | ❌ |

改内容/附件/范围后：`packed → queued` 并提示「已失效的打包结果需要重跑」，不静默复用旧包。

#### 6.0.8 接口与数据改动

| 层 | 改动 |
| --- | --- |
| `task.yaml` | 新增 `brief`、`attachments[]`、`references[]`（加法键，旧任务缺省为空） |
| `production.task.create/update` | 接受上述字段；`update` 按 §6.0.7 状态边界校验 |
| 新命令 `production.task.attach/detach` | 登记/移除附件；来源限 `.input/` 或本线资产目录 |
| REST | `POST/DELETE /api/production/lines/{id}/tasks/{taskId}/attachments`；建任务接受 `attachment_sources` |
| 提示词 | `packerUserPrompt` / `executorUserPrompt` 增任务内容、附件、引用、项目文档与记忆段 |
| 记忆 | `tree.agent` 新增 `agent.memory.get/record`；产线只加 `MemoryPort` 适配器与 run 台账 `memory_hash/sources` |
| `pack.json` | 增 `attachments[{path,sha256,size,type}]` 快照 |
| `tree.agent` | `agent.worker.run` 增可选 `attachments`；`SubagentTurnRequest` 透传到现有 vision 通道 |

#### 6.0.9 验收

1. 新建任务填内容 + 2 条验收 + 1 张图 + 1 个 md，附件立即出现在表单，保存后落到 `.input`；
2. 只填标题保存可建草稿，但「加入队列/开始」被拒并指出缺内容/验收。
3. 文本附件能被打包模型 `read`；图片在支持视觉的模型下进入多模态，非视觉模型有预检警告。
4. PDF/Office 附件有「不可直接读取」标识，不伪造内容。
5. 打包后改附件 → 任务回 `queued` 并提示重打包；旧包不再被执行。
6. 附件路径越界、超限、同名覆盖、目录/符号链接均被拒。
7. 执行提示词包含任务内容、附件清单与引用文件；改动不依赖手改 YAML。

### 6.1 任务看板

```text
[全部] [进行中] [待你决定] [阻塞] [已完成]        [按计划派发] [暂停产线]
T1  done       门控通过 · 2 个产物
T2  running    执行中 · 第 1 次 · 8.2k tokens
T4  packing    打包中 · 3m
T7  blocked    门控失败 · dart analyze 2 errors      [恢复] [取消]
```

- 默认筛选 `进行中 + 待你决定 + 阻塞`，`已完成` 需手点。
- 每行显示：ID、标题、状态、依赖未满足标记、写域摘要、重试/提问次数、预算。
- 「按计划派发」先调 `queue/plan`，弹出可并行批次确认，不直接批量打出去。
- 手动派发与批量派发都遵守依赖/并行/写域护栏；被拒时行内说明原因。

### 6.2 任务详情（右栏详情页）

点任务行 → 右栏自动切到「任务详情」窗口；关窗口不清选中，再次点同一行重新打开。
窗口与文件/设置共享右栏宿主，窄于 360px 时按宿主规则折叠。

```text

状态：执行中 · 第 1 次 · 8.2k tokens · 预算 8.2k/50k
[概览] [计划] [打包] [执行与门控] [消息与专家] [台账]
```

| 页签 | 内容 |
| --- | --- |
| 概览 | 状态、`blocked_reason`、`last_error`、重试/提问、最近决策、记忆来源/hash/是否截断 |
| 计划 | 任务内容（Markdown 可编辑）、需求五栏、验收、依赖、读写域、优先级、`kind`、附件与引用；非终态可编辑 |
| 打包 | `pack.json` 摘要（文件数/字节/基线命令/风险点）、`pack.md` 打开 |
| 执行与门控 | 改动文件、diff 摘要、门控命令与输出（截断+完整路径）、重试历史 |

- 切换产线时关闭该窗口并清掉选中任务，避免把 A 线任务详情留在 B 线上下文。

### 6.3 主控条与暂停

- `立即决策` 回包展开显示：动作、理由、被哪条护栏降级、是否生效。
- `暂停产线` 立即停止自动派发；已经 `running` 的任务继续跑完，不强制中断。
- `恢复` 写回执行中并立即决策一次。
- 连续 3 次决策失败自动暂停，首屏显示「主控连续失败，已暂停」+ 原因 + 恢复按钮。

### 6.4 记忆与项目知识（直接套 agent）

**结论：直接复用 `tree.agent` 的记忆，不在产线里自建第二套。**
产线只做「消费方」：读记忆走 agent 的端口，写记忆也走 agent 的端口；
产线不读 `.self/memory.md`、不缓存记忆正文、不做自己的记忆裁剪/排序。

#### 6.4.1 三个概念分开

| 概念 | 归属 | 说明 |
| --- | --- | --- |
| **Agent 记忆** | `tree.agent` | 当前 MVP = `.self/memory.md` + 会话压缩摘要；后续升级为结构化/向量记忆也只改 agent |
| **项目文档** | 产线 `line.yaml.docs.memory_manifest` | 明确列出的项目文档（project-status/work-log/known-issues…），是「资料」不是「记忆」 |
| **任务输入** | 产线 `task.yaml` | `brief / acceptance / references / attachments`，只属于本任务 |

> `docs.memory_manifest` 保留原名以兼容存量，但 UI 标为「项目文档」；产线不再把它叫记忆，
> 也不在产线里实现第二套记忆存储。

#### 6.4.2 记忆端口（`tree.agent` 执行站）

| 命令 | 入参 | 回包 | 用途 |
| --- | --- | --- | --- |
| `agent.memory.get` | `{agent_id, purpose: prepare\|pack\|run, budget_chars, kind?}` | `{text, sources[], hash, version, truncated}` | 取**已由 agent 裁剪/排序/格式化**的记忆块 |
| `agent.memory.record` | `{agent_id, source: production_line, line_id, task_id, status, summary, artifacts[], at}` | `{accepted, id?}` | 把任务结果作为记忆候选交给 agent，由 agent 决定是否吸收 |

- `agent_id` 取 `line.yaml.executor.agent_id`（员工身份），不是「谁点了派发」。
- `text` 是 agent 渲染好的 Markdown；产线**不解析、不二次裁剪**，只原样注入提示词。
- `sources` / `hash` / `truncated` 只用于台账与 UI 展示，不落产线数据。
- `version` 供未来记忆升级时做兼容判断；产线不按内部结构分支。
- 记忆不可用（命令缺失/超时）⇒ 空块 + 台账记 `memory_unavailable`，任务继续，不 fail-closed。

#### 6.4.3 注入点与预算

| 场景 | 是否注入 | `purpose` | 默认预算 |
| --- | --- | --- | --- |
| 准备阶段侦查 | ✅ | `prepare` | 4 000 字 |
| 打包（packer） | ✅ | `pack` | 6 000 字 |
| 执行（executor） | ✅ | `run` | 6 000 字 |
| 主控 tick | ❌（v1） | — | — |

- 主控保持「快照决策」，不把记忆塞进每 tick，避免成本与漂移；后续需要时再单列开关。
- 预算由调用方传入，**裁剪由 agent 完成**；产线只显示 `truncated`。
- 同一次任务里打包与执行各自取最新记忆；不把记忆正文写进 `pack.json`。

#### 6.4.4 写入路径

- 任务进入终态（`done / blocked / cancelled`）后，产线调用一次 `agent.memory.record`
  （fire-and-forget，失败只记日志，不影响任务结果）。
- 记录内容只放**结果摘要**：任务标题、状态、改动文件、门控结果、决策动作；
  不放完整对话、不放代码全文、不放附件正文。
- 当前 MVP 由 agent 写入自己的候选队列（agent 自有存储）；**产线不写 `.self/memory.md`**。
  后续 agent 记忆升级时，由 agent 消费候选队列并决定合并策略。

#### 6.4.5 保证「逻辑只存一次」

1. 记忆读取、裁剪、排序、格式化只在 `tree.agent` 的 memory 实现里；
   产线只有一个 `MemoryPort` 适配器（`get/record` 两个方法）。
2. 产线不读 `.self/memory.md`、不存记忆副本、不写记忆文件。
3. 提示词里只有**一个**「## 记忆」段，准备/打包/执行共用，不按角色各写一套格式。
4. `pack.json` / run 台账只存 `memory_hash` 与 `sources`，不存正文。
5. 项目文档读取收敛为一个共享 `projectContext` helper（准备/打包/执行共用），
   与 agent 记忆彻底分开，避免两套「记忆」并行。
6. 未来 agent 记忆升级只改 `tree.agent` 实现；`agent.memory.get/record` 的命令与回包形状保持稳定，
   产线零改动（契约测试钉住形状）。

#### 6.4.6 记忆与任务输入的区别

- 附件/内容变化 ⇒ 旧 `pack` 失效（任务输入变了）。
- 记忆变化 ⇒ **不**让 `pack` 失效；执行用最新记忆，台账同时记录打包与执行两个 `memory_hash`。
- 记忆不是事实真源：状态机、验收、写域仍以 `task.yaml` 为准，记忆只影响提示词。

#### 6.4.7 UI 与验收

- 任务详情「概览」显示：记忆来源数、字数、是否截断、`memory_hash` 前 8 位；
  展开可看 `sources`（路径/章节），不显示全文。
- 台账每条 run 带 `memory_hash` 与 `memory_sources`，便于复盘「当时用了哪份记忆」。
- 验收：同一任务打包/执行提示词都出现记忆块；`pack.json` 无记忆正文；
  agent 记忆升级后产线无需改动即可继续工作；记忆不可用时任务仍能完成并留下原因。

### 6.5 文档维护边界

**现状：产线只写产线资产，不维护项目文档。**

| 文档类型 | 谁写 | 现状 |
| --- | --- | --- |
| 产线资产（`docs/production_lines/<line>/`） | 产线自动写 | `recon/scope/plan/decisions/audit`、每任务 `acceptance/pack`；这是产线的审计轨迹 |
| 项目文档（`docs.memory_manifest` 里的 project-status/work-log/known-issues/handover） | 默认没人写 | 只作为打包/执行的项目记忆**读入**，执行流程没有「更新文档」步骤 |
| README / CHANGELOG 等 | 默认没人写 | 同上；代码任务不会自动改 |

规则：

- **项目文档默认只读**：代码任务的 `write_scope` 不含 `docs/` 时，执行站拒绝写文档。
- 需要文档维护时，计划里**单独列一个文档任务**：`write_scope` 只含目标文档，`read_scope` 含代码；
  与写同一文档的代码任务串行，不并行；验收写明「哪份文档、哪些章节」。
- 产线资产自动写，不计入项目文档维护；它不能替代 work-log/known-issues。
- **不自动更新** `project-status / work-log / known-issues`；这些是人工或显式文档任务，
  避免多任务并发写同一份文档、也避免产线替用户做项目决策。
- 文档任务仍受门控、写域、读取预算约束；不能借文档任务绕过代码写域。
- 文档归一化属于初始化前置写入（§4.1.2），不是任务，也不占任务槽。

## 11. 交互规则

1. **刷新**：工作台可见时订阅 `broadcast.task_state`；断开或插件未实现推送时 3s 轮询。
   窗口不可见时停轮询，恢复可见时先拉一次 REST 快照。
2. **动作反馈**：按钮就地转圈 + 防重复；失败在卡片/行内显示，不用全屏错误。
3. **确认**：删除产线、取消任务、专家开写工具、改写域需二次确认；其余动作一步完成。
4. **折叠**：今日分区、工具区、详情页签同一时间只展开一个；展开/收起不改变上方内容位置。
5. **滚动**：任务看板与台账虚拟化；详情抽屉独立滚动；工作台整体滚动不嵌套。
6. **返回**：详情抽屉关闭回到列表原位置；准备四步可回退，不丢草稿。
7. **无聊天**：不提供与产线对话的输入框；补充说明只落在对应步骤/任务字段。

## 12. 与现有 UI 平台的约束

- 产线是活动栏第 4 项，与 Agent 并列；切页用 `IndexedStack` 保持会话与工作台状态
  （现有实现已如此）。
- 中栏是工作台唯一承载区；折叠中栏时沿用现有 chevron 机制。
- 右栏继续承载文件窗、设置、插件管理与**任务详情**；任务详情是 `RightPanelEntry`（id `productionTask`，
  `autoOpenOnSelection`），不新增中栏抽屉或第三套详情容器。
- 视觉沿用 `AppRadius`、主题 token、字重/字号设置；状态色用 `ColorScheme`
  的 primary/tertiary/error/secondary，不新增硬编码色值。
- UI 只经 REST/站点与插件通信，不读插件数据目录；产物打开走 files 插件。
- **就绪门判据只在后端**：UI 只能展示 `ready/missing/progress`，不能传 `ready=true` 覆盖；
  `understand / task.create / task.attach / queue.dispatch / start / tick` 统一做门控校验。

## 13. 明确不做

- 不做与产线的聊天流；不做「问产线一句，它直接改需求」。
- 不做无人值守连跑一整天；自动推进只到当前队列跑完。
- 不做跨产线调度、不做产线互调 Agent 会话。
- 不做自动 `commit/push`；只给 diff 摘要与建议提交信息。
- 不做移动端/窄屏专门布局；桌面优先。
- 首版不提供「强制派发」开关；护栏被拒就是被拒。
